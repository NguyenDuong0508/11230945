# Part 3 — Scalable processing protocol

## Input and isolation

Resolve `active_panel.json` with the Part 2 verifier, including Bronze lineage and all Silver partitions. No event or retrospective audit table is used in the analytical workloads. The eight-column benchmark projection is `CERT`, `REPDTE`, `ASSET`, `DEP`, `ROA`, `STNAME`, `DQ_ROE_ABS_GT_100`, `EQ`. The 1× input preserves every observed record and these eight values from the verified Silver panel. Staging rewrites one Snappy Parquet file per quarter on the same local filesystem for every scale, with row groups capped at 65,536 rows. This is a controlled narrow-schema processing experiment, not a benchmark of all 54 Silver columns or a reproduction of Part 1's storage experiment.

The 5× and 10× inputs replicate complete bank histories, using `CERT + replica_index × max_observed_CERT` to create disjoint identities. Dates, state, values and missingness are unchanged. Every staged file is read back and compared to its expected table; the manifest records row counts, file sizes and checksums. The synthetic panels preserve distribution and temporal structure by construction, but do not represent additional banks, independent samples, a different crisis distribution or real cross-sectional growth. They are deleted from local scratch after the experiment and never enter modelling. The number of physical quarterly files is constant; file/row-group sizes increase with scale.

## Workloads

All engines use native operations, return one ordered row per reporting quarter and apply the same null semantics. Counts are integers; all-null sums and means are null. Dates, counts, nulls and output fields must match exactly; floating-point results are compared with relative tolerance 1e-9 and absolute tolerance 1e-7 to allow different reduction orders. Every warm-up and measured result is stored and compared, and synthetic counts/sums must scale proportionately while means remain invariant. The small integration fixture checks known temporal gaps, all-null aggregates, missing state, filtered dates and multiple peer groups.

| Workload | Definition |
|---|---|
| `quarter_summary` | Filter `REPDTE >= 2000-03-31`; count observations, sum assets/deposits, mean ROA, count extreme-ROE flags per quarter. |
| `adjacent_growth` | Order by CERT and report date, lag previous quarter index and assets; compute asset growth only when exactly one calendar quarter apart, previous assets are positive, and current assets are non-null. Summarize total rows, adjacent pairs, valid growth counts and mean growth per quarter. No gap filling. |
| `peer_join` | Compute mean reported ROA for nonempty, non-null state/quarter groups with non-null ROA; left join many-to-one to all observations; summarize row count, matched deviations and mean absolute deviation per quarter. This descriptive, self-inclusive peer statistic is not a production feature or risk score. |

pandas uses PyArrow Dataset projection and the same date predicate before eager vectorized operations. Polars uses `scan_parquet`, native expressions and lazy execution. Spark uses SQL DataFrame expressions, windows and joins, not Python UDFs. Spark may choose broadcast or shuffle joins; inspect the recorded plan rather than assert a predetermined join strategy. The chronological window needs ordering and does not apply a date cutoff that discards its required history.

## Experimental protocol

- 1×: pandas, Polars and local PySpark (`local[2]`) for each workload. 5×/10×: pandas and Polars only, to test single-machine scaling. An additional 1× Polars single-thread scenario per workload provides a controlled thread-count comparison. Spark is demonstrated on the complete actual-scale projection, not on a cluster or the synthetic larger panels.
- 24 scenarios, one warm-up and three measured trials each (96 timed invocations, 72 measured). Scenario order uses seed 11230945. Each scenario starts a fresh Python process; repetitions share that process and Spark session. An additional untimed parity-checked execution captures the plan for each non-pandas scenario (15 additional invocations). No Spark persistence or explicit cache flush. OS and engine warm state can influence results.
- Input staging, engine imports/initialization (Spark JVM startup included), plan extraction, parity checks and figure creation are excluded from measured elapsed time. The query path includes reading, computation, materialization and normalization of the small output. The reported `input_rows` is the logical selected row count for the filtered summary and the complete row count otherwise; it is not measured rows physically read.
- Two-thread limits are applied to Arrow CPU and I/O pools and common numerical-library environment variables, Polars thread pool and Spark local worker slots; these are not identical CPU utilization guarantees. The single-thread Polars case sets the environment before import. Record versions, CPU affinity, RAM and Java. No forced CPU affinity or claim that the machine has two physical cores.
- Sample current RSS of the worker and its descendants every 20 ms and at boundaries, including Spark JVM. Report baseline, sampled peak and increment above baseline. This avoids inherited Linux `ru_maxrss` high-water marks, but shared pages may be counted more than once and short peaks may be missed. Allocator retention between repetitions may affect baseline and increment. Compare the whole process footprint, not isolated dataframe allocations.
- Medians and inclusive IQRs summarize three measurements per scenario. Report the observed speedups, scaling ratios, and logical rows per second; do not extrapolate a fitted model to claim a cluster break-even point. A failed engine, incomplete trial or parity mismatch blocks publication; the implementation does not silently omit a scenario. If resource limits prevent 10×, retain the failure and revise the explicitly documented protocol before rerunning, rather than claim success.

## Execution plans and scaling interpretation

Read the full optimized Polars plan (`PROJECT`, `SELECTION`, aggregation, sort, `shift().over()`, join) and Spark formatted plan after an action (`ReadSchema`, `PushedFilters`, partial/final aggregate, `Exchange`, `Sort`, `Window`, join and adaptive operators). Projection pruning and date filtering reduce work; a window may need sort and materialization; grouping or join can require state or shuffle. A Spark local exchange is not measured network I/O. A logical plan does not establish actual streaming execution. The default Polars engine is used; no claim that every operator runs out of core.

The one- and two-thread Polars measurements yield speedup S=T1/T2, efficiency S/2 and an apparent serial fraction f=2/S−1 under the ideal two-worker Amdahl model. An estimate outside [0,1] indicates the model/measurement assumptions do not fit and must not be clipped or interpreted as a physical fraction. Memory bandwidth, I/O, scheduling, cache and query planning can violate the model. This is a diagnostic, not a prediction of multi-node performance.

The cluster decision must consider observed 1× and 5×/10× latencies, RSS versus available memory, workload shape, input footprint and service deadlines. If single-node Polars meets operational constraints, local processing is preferable for this dataset. A real cluster may be justified by out-of-memory workloads, concurrency, time constraints or data locality, but actual break-even requires a separate multi-node trial including network, provisioning, storage and cost. Local Spark times and synthetic replication do not establish that threshold.

## Reproduction and handoff

Install Java 17 or later, configure `JAVA_HOME` if necessary, and install the pinned `requirements.txt`. Run the full test suite with no skips. Use `python run_part3.py run --workspace PATH --scratch LOCAL_PATH`, then `python run_part3.py verify --workspace PATH`. The scratch path must be outside the workspace, with adequate disk and RAM. Avoid concurrent pipeline runs. The evidence directory includes complete worker results, plans, staging metadata, environment, summary tables, figures and manifest. `active_processing.json` is published only after evidence checks. The verification command checks hashes and compares all saved trial outputs again; it does not rerun the engines. Part 4 consumes the verified original Silver panel, not these benchmark files or summaries.
